# ATHR — خطة ما بعد الإطلاق

> مسودة استراتيجية للنقاش. لا شيء هنا ملزم حتى يعتمده المالك؛ الخطة الملزمة الحالية هي `ATHR_MASTER_PLAN.md` (W0–W7).
> آخر تحديث: 2026-09-30

## المبدأ

بعد الإطلاق التجريبي الأولوية ليست "مزايا أكثر" بل ثلاثة أشياء بالترتيب:
1. **العميل يبدأ بسرعة** (من التسجيل لأول فاتورة في أقل من ساعة).
2. **العميل يفضل معانا** (يفتح النظام كل يوم ويعتمد عليه).
3. **العميل يدفع ويجيب غيره** (تحصيل سهل + سبب يخليه يرشّحنا).

كل ميزة تحت مرتبطة بواحد من الثلاثة. أي ميزة لا تخدم واحدًا منهم تتأجل.

## المرحلة 0 — أول 4–6 أسابيع بعد الإطلاق التجريبي (تثبيت)

لا مزايا كبيرة. نسمع ونصلّح.

| البند | السبب |
|---|---|
| قياس الاستخدام (activation, retention، أكثر الشاشات استخدامًا، أين يتوقف العميل) | بدونه كل قرار بعد كده تخمين |
| استيراد المنتجات والأرصدة من Excel | أكبر عائق لبدء أي محل: إدخال مئات الأصناف يدويًا |
| مركز مساعدة + فيديوهات قصيرة + زر دعم (واتساب) داخل النظام | يقلل وقتك في الدعم مع كل عميل جديد |
| طباعة ملصقات الباركود | أغلب المحلات الصغيرة ليس عندها باركود على المنتجات |
| سجل ملاحظات العملاء التجريبيين وتصنيفها | يحدد ترتيب المراحل التالية بالبيانات |

## المرحلة 1 — الشهور 1–3: تطبيق الموبايل + القنوات اليومية

### 1.1 تطبيق صاحب المحل (الفكرة الأساسية)

يُبنى على **نفس الـAPI الحالي** (لا backend جديد). يُقسَّم على ثلاث خطوات حتى لا يصبح مشروعًا ضخمًا مرة واحدة:

| الخطوة | المحتوى | القيمة |
|---|---|---|
| **أ — المتابعة** (4–6 أسابيع) | مبيعات اليوم لحظيًا لكل فرع، الورديات وفروق النقد، المخزون الناقص، إشعارات push (بيع كبير، مرتجع، فرق درج، صنف نفد) | "محلي في جيبي" — أقوى سبب يفتح به التطبيق كل يوم |
| **ب — الإدارة** | تعديل سعر، إضافة منتج بكاميرا الموبايل (مسح الباركود)، الموافقة على تحويل/مرتجع/خصم، استلام مشتريات، جرد بالكاميرا | يدير من غير ما يكون في المحل |
| **ج — البيع من الموبايل** | POS كامل على الموبايل/التابلت: كاميرا للباركود، طابعة بلوتوث، يعمل offline بنفس بروتوكول المزامنة | يفتح شريحة جديدة: محل صغير/كشك/مندوب **بدون كمبيوتر** — ممكن تكون باقة أرخص للدخول |

**قرار تقني مقترح:** React Native (Expo) — تطبيق واحد لأندرويد و iOS، ويعيد استخدام `@athr/contracts` و`@athr/domain-core` (نفس قواعد المال والكميات والباركود). البديل الأسرع للخطوة (أ) فقط: PWA من لوحة الإدارة الحالية، لكنه أضعف في الإشعارات والكاميرا والـoffline.

**ما نجهّزه من الآن بتكلفة قليلة** (حتى لا يكون التطبيق مكلفًا لاحقًا):
- الـAPI يبقى typed ومستقرًا (موجود عبر `@athr/contracts`)؛ لا منطق أعمال في واجهة الـadmin.
- جدول إشعارات لكل tenant (مخطط في W0) يصبح مصدر الـpush.
- صلاحيات الموبايل = نفس نظام الصلاحيات الحالي؛ الميزة تُفتح بمفتاح في الباقة (`mobile.app`).

### 1.2 واتساب

في السوق المصري واتساب هو قناة العمل. مزايا صغيرة وأثرها كبير:
- إرسال الفاتورة للعميل على واتساب بدل الورق.
- تقرير يومي لصاحب المحل (مبيعات، أرباح، نواقص) — يصل حتى لو لم يفتح التطبيق.
- تنبيهات (نفاد صنف، فرق نقدية).

### 1.3 تحصيل الاشتراكات أونلاين

حاليًا التفعيل يدوي (D4). بعد أول ~30 عميل يصبح التحصيل اليدوي عبئًا:
- بوابة دفع محلية (Paymob / Fawry / InstaPay) + تجديد تلقائي + فاتورة اشتراك.
- ترقية/تنزيل الباقة ذاتيًا من النظام (البنية جاهزة: الباقات بيانات).

### 1.4 الفاتورة/الإيصال الإلكتروني (مصلحة الضرائب)

التكامل مع منظومة الإيصال الإلكتروني ميزة بيع قوية جدًا للمحلات الملزمة بها، وقد تكون شرط شراء.
**يحتاج تحققًا من المتطلبات والمواعيد الحالية قبل التخطيط** — لا أفترض تفاصيلها هنا.

## المرحلة 2 — الشهور 3–6: الاحتفاظ بالعميل وزيادة قيمته

| الميزة | لماذا |
|---|---|
| **البيع الآجل وحسابات العملاء** (مديونية، تحصيل، كشف حساب) | شائع جدًا في السوق؛ غيابه يمنع محلات كثيرة من الاعتماد الكامل على النظام |
| **حسابات الموردين والمصروفات وقائمة أرباح وخسائر بسيطة** | صاحب المحل يريد "كسبت كام الشهر ده؟" وليس محاسبة كاملة |
| **ولاء العملاء** (نقاط، محفظة، حملات واتساب/SMS للعملاء المنقطعين) | يرفع مبيعات العميل نفسه → سبب مباشر للتجديد |
| **اقتراح طلبات الشراء** (حد إعادة الطلب، أصناف راكدة، توقع بسيط من تاريخ المبيعات) | يحوّل النظام من "تسجيل" إلى "نصيحة" |
| **متجر إلكتروني بسيط / رابط طلب** مربوط بالمخزون | قناة بيع إضافية بدون نظام ثانٍ |
| **تكامل ماكينات الدفع والمحافظ** في البيع | يقلل أخطاء الكاشير ويسرّع الدفع |
| **برنامج إحالة** (شهر مجاني لمن يرشّح عميلًا) | أرخص قناة اكتساب عملاء |

## المرحلة 3 — الشهور 6–12: التوسع

| الاتجاه | الوصف |
|---|---|
| **مساعد ذكي بالعربي** | "أكتر صنف كسبني الشهر ده؟"، "إيه اللي لازم أطلبه؟" — فوق التقارير الموجودة |
| **أنواع تجارة جديدة كـpresets + موديولات** | مطاعم/كافيهات (طاولات، شاشة مطبخ)، صيدليات (تعتمد على تتبع الدفعات W2b)، ورش/خدمات |
| **API عام + webhooks** | يفتح الربط مع المحاسبة والتوصيل والمتاجر، وشركاء يبنون فوقنا |
| **برنامج موزعين/شركاء** | محاسبون ومحلات أجهزة يبيعون النظام بعمولة، مع لوحة للشريك |
| **باقات أجهزة** | شراكة مع مورد (كاشير + طابعة + ماسح) — "افتح محلك بكرة" |
| **Franchise / مجموعة شركات** | تقارير مجمعة وتسعير مركزي لعدة كيانات |
| **التوسع الإقليمي** | السعودية (الفوترة الإلكترونية ZATCA)، الخليج — يحتاج عملات وضرائب متعددة (البنية تدعم العملة لكل tenant) |
| **تمويل للتجار** (على المدى البعيد) | بيانات المبيعات تصلح أساسًا لتمويل بضاعة عبر شريك مالي — مصدر دخل يتجاوز الاشتراك |

## كيف نختار الترتيب الفعلي

الترتيب أعلاه افتراض. بعد المرحلة 0 يُعاد ترتيبه حسب:
1. **ما يطلبه العملاء التجريبيون فعلًا** (عدد الطلبات × حجم العميل).
2. **ما يمنع الشراء** (ميزة ناقصة تجعل العميل لا يشترك) قبل ما يحسّن تجربة مشترك موجود.
3. **التكلفة:** ما يُبنى فوق ما هو موجود أولًا (واتساب، استيراد Excel، ملصقات) قبل المشاريع الكبيرة.

## أسئلة مفتوحة للمالك

- تطبيق الموبايل: نبدأ بالمتابعة فقط (أسرع للسوق) أم ننتظر حتى يكون فيه إدارة كاملة؟
- هل شريحة "محل بدون كمبيوتر" (POS على الموبايل) هدف، أم العميل المستهدف عنده كاشير دائمًا؟
- هل العملاء التجريبيون الأوائل ملزمون بالإيصال الإلكتروني؟ (يحدد أولوية 1.4)
- السوق الأول بعد مصر؟ (يحدد متى نستثمر في ضرائب/عملات متعددة)
